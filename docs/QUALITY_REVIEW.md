# 项目质量检查记录

检查日期：2026-09-16。检查范围包括当时工作区的规则引擎、公共调度、SQLite 持久化、Agent/RSI 可见上下文、经验隔离、游戏切换与回放，以及文档。以下结果对应这次检查，后续验证单独记录在文末。

## 结论

四款游戏的主要流程通过了现有测试，但检查仍发现了创建失败后残留记录、回放显示旧帧、切场后经验写错玩家，以及手动经验缺少游戏类型的问题，修复和验证方法见下表。这次检查使用临时数据和模拟模型，未修改真实实验数据库或调用付费模型服务。

## 验证方式

使用 Node.js 22.20.0、项目锁文件依赖和本地 Chromium。单元/集成测试使用临时 SQLite 与模拟模型；浏览器测试使用独立服务和临时目录。

本次结果：类型检查通过；10 个测试文件、162 项单元/集成测试通过；27 项浏览器测试完整通过，最后的终局原因调整后补跑三国杀回放回归也通过；生产构建、格式与 `git diff --check` 通过。19 份 Markdown 的 184 个相对文件链接目标均存在。

```bash
./run.sh typecheck
./run.sh test

CHROMIUM_PATH=/path/to/chrome E2E_PORT=43931 ./run.sh test:e2e
```

若本机代理转发了回环请求，先为 localhost 配置 NO_PROXY/no_proxy，或在浏览器测试命令中取消代理变量。README 与 docs 下 Markdown 的相对文件链接也检查其目标存在；该检查不验证外部网站和标题锚点。

## 后续维护项与验证边界

1. `web/main.tsx` 与 `web/MultiGameArena.tsx` 均超过千行，各自维护刷新、创建、回放和错误状态。可以提取公共的观战请求与帧校验 hook，再拆分创建和经验面板，减少两套逻辑不一致的问题。
2. 存储和旧前端仍有 `any`，根 tsconfig 未包含 tests。Vitest/Playwright 通过不代表测试代码也通过了 TypeScript 静态检查。当时仓库没有 CI 工作流；可增加测试专用 tsconfig，再将类型、单元、构建和关键浏览器检查接入 CI。
3. 比赛列表没有分页，旧应用会周期性读取全部玩家经验。每个事件还保存完整压缩状态，同步 SQLite 和历史重建在长期、大并行实验下的开销尚未测量。本次未做大库压测或长时稳定性验证，无法据此估计吞吐量。
4. 管理令牌只保护写操作，观战和导出接口包含全知信息，部署面向受信任实验者。国际象棋使用 chess.js 的子力判和，未穷举罕见死局；中国象棋不实现长捉或将捉混合竞赛裁定。详细范围见[游戏目录](games/README.md)。
5. 模拟模型验证了协议、信息隔离和经验写入与复用。真实模型的棋力、费用、供应商兼容性和 RSI 收益需要另行实验；本次也未查询依赖漏洞数据库。
